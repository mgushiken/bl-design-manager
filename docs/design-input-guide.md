# BlackLine 設計に必要な情報の候補

## 1. この資料の目的と現時点の前提

将来、別プロジェクトで構築する情報収集 Agent と設計 Agent が扱う情報の候補を整理する。本資料は構想検討の参考一覧であり、実案件の資料提出依頼ではない。構想全体は [プロセス・情報収集・Agent 分担の構想](agent-concept.md) を参照する。

以下の設計手順・成果物・完了基準は、将来 Agent が支援する業務の参考案。このリポジトリでは情報の必要性、入手方法、Agent が扱える粒度を検討する。BL と ERP のどちらがデータの正本を持つかなどは、案件ごとの確認対象とする。

## 2. 最初にそろえるもの

まず次の五つがあれば、要件と設計項目の対応付け、実現性の確認、未決事項の抽出を始められる。不足は推測で補完せず、課題として管理する。

| 優先 | 入力資料・情報           | 確認する内容                                                           | 主な確認先                            |
| ---- | ------------------------ | ---------------------------------------------------------------------- | ------------------------------------- |
| 1    | Markdown 要件定義書一式  | 対象ファイル、版、承認状態、要件 ID、関連図表、対象外                  | 業務責任者・要件定義担当              |
| 2    | BL の契約・利用範囲      | 製品／モジュール名、対象地域・会社、利用可能な機能、追加契約の要否     | BL 管理者・契約担当・導入パートナー   |
| 3    | 現行／将来の業務フロー   | 入金消込・勘定照合の開始から承認・ERP 反映まで、担当と締切             | 経理・債権管理担当                    |
| 4    | システム構成と連携一覧   | ERP の製品・版・会社構成、銀行等の外部システム、データの方向と正本     | ERP・連携基盤担当                     |
| 5    | データ例と BL の技術資料 | 匿名化した残高・明細・請求・入金例、項目定義、対象環境の設定／連携仕様 | データ担当・BL 管理者・導入パートナー |

要件定義書で既に決まっている事項は、その記載と要件 ID を参照する。要件に記載がない事項だけを追加確認する。

## 3. 製品の役割を切り分ける

公開情報では、Account Reconciliations は勘定照合の標準化・統制、Transaction Matching は明細データをルールで突合する機能、Cash Application は入金と請求の消込に関わる機能として説明されている。同じ「照合・消込」という日本語でも、対象業務と利用製品を分けて要件を割り当てる。[公式: Account Reconciliations](https://www.blackline.com/products/financial-close/account-reconciliations/)、[公式: Transaction Matching](https://www.blackline.com/products/financial-close/transaction-matching/)、[公式: Cash Application](https://www.blackline.com/invoice-to-cash/cash-application/)

BL と ERP の双方向連携は公開情報で説明されているが、個別の接続方式、書き戻せる項目、API、仕訳・消込の確定タイミングは案件の契約・環境・ERP 側仕様で確認する。公開製品紹介だけで設定値や接続方式を確定しない。[公式: ERP Integration](https://www.blackline.com/erp-integration/)

## 4. 設計領域別の確認事項

以下は本案件向けの設計確認観点であり、BL の標準機能として提供されることを保証する一覧ではない。

| 設計領域           | 必要な情報・決定事項                                                                                           | 設計成果物                           |
| ------------------ | -------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 対象範囲・責任分界 | 会社、拠点、業務、製品、導入段階、対象外、BL／ERP／人手の担当範囲、正本                                        | スコープ・システム構成・責任分界     |
| 業務フロー         | 実行条件、頻度、担当、入力、処理、出力、承認、差戻し、取消、月次締めとの関係                                   | 業務フロー・状態遷移                 |
| 組織・マスタ       | 会社・勘定・顧客・銀行口座等のキー、階層、管理元、有効期間、変更・同期方法                                     | マスタ・コード対応設計               |
| 入金消込           | 対象請求と入金、照合キー、優先順位、部分入金、合算入金、過不足、手数料、為替、前受、返金、取消、手動判断の境界 | 消込ルール・例外処理設計             |
| 勘定照合           | 対象勘定、残高と証憑、期間、照合単位、差異の分類・解消、繰越、担当・承認、再オープン条件                       | 勘定別照合・承認設計                 |
| 明細突合           | データソース、1:1／1:N／N:N の要否、キー、許容差、日付範囲、ルール順序、重複候補、未突合、解除                 | マッチングルール設計                 |
| 画面・設定         | 対象製品で利用できる設定項目、入力必須・制約、一覧条件、テンプレート、標準機能との差分                         | 設定値一覧・操作設計・適合／差分一覧 |
| データ連携         | 方向、送受信元、方式、実行契機、項目、型、桁、文字コード、日付・時差、通貨、小数・丸め、件数・サイズ           | 連携一覧・項目マッピング             |
| 連携の整合性       | 業務キー、重複判定、全件／差分、順序、再送、途中失敗、応答、件数・金額照合、ERP 反映の確認方法                 | 整合性・再処理設計                   |
| 会計・締め         | 計上日・会計期間、締め済期間、仕訳生成の要否、承認前後の更新可否、取消・逆仕訳、遡及修正                       | 会計処理・締め制御設計               |
| 権限・認証         | ロール、会社別参照範囲、作成と承認の職務分離、代理、入退社、SSO、連携用アカウント                              | 権限マトリクス・認証設計             |
| 証跡・統制         | 操作・設定変更・承認・連携履歴、証憑、保持期間、閲覧・出力権限、監査提出方法                                   | 証跡・保存設計                       |
| 非機能・運用       | 通常／ピーク件数、処理期限、利用時間、障害検知、通知先、復旧目標、手動代替、問い合わせ責任                     | 非機能・運用設計                     |
| 環境・移行         | 開発／検証／本番の有無、環境差分、設定反映方法、初期マスタ・残高・未消込、移行リハーサル、切替と戻し条件       | 環境・移行設計                       |

各ルールは説明文だけでなく「入力例 → 適用条件 → 期待結果 → 例外時の対応」を残す。金額の許容差や保持期間などの値は、業務責任者の判断と製品制約を確認して確定する。

## 5. 要件から設計へ進める手順

1. 要件定義書を読み、要件 ID ごとに対象業務・製品・入力・出力・制約・受入条件を整理する。ID がなければ元の見出しと対応する ID を付ける。
2. 要件を上記の設計領域へ割り当て、不足情報と矛盾を洗い出す。
3. 製品資料、利用環境、導入担当への確認で実現方法を判定する。「標準設定」「外部連携」「運用対応」「追加検討」などに分類し、根拠を記録する。
4. 業務フローと責任分界を合意し、設定・データ・連携・権限・例外処理を具体化する。
5. 通常、例外、取消、再処理、締め境界のサンプルを使って、設計全体の整合性をレビューする。
6. 未決事項の解消または承認済みの保留条件を記録し、設計版と承認を確定する。

設計着手には全情報の確定を必須としない。ただし、対象製品・連携方式・会計結果に影響する未決事項を残したまま、関連する詳細設計を確定しない。

## 6. 推奨する設計書構成

Markdown で管理する場合の構成例。規模が小さければファイルを統合してよい。

```text
requirements/                  # 入力する要件定義書
docs/design/
  00-overview.md               # スコープ、前提、構成、責任分界
  01-business-flow.md          # 業務フロー、状態、例外
  02-blackline-settings.md     # 製品別設定と実現性の根拠
  03-data-and-mapping.md       # マスタ、キー、項目対応
  04-interfaces.md             # 連携、エラー、整合性、再処理
  05-roles-and-controls.md     # 権限、承認、証跡
  06-operations-and-migration.md
  07-traceability.md           # 要件・設計・将来の試験の対応
  08-open-issues.md            # 未決事項と判断履歴
```

設計項目の最小記録例:

| 項目          | 記録内容                                           |
| ------------- | -------------------------------------------------- |
| 設計 ID／名称 | 一意の ID と処理・設定の名前                       |
| 対応要件      | 要件 ID、元ファイルと見出し                        |
| 対象・前提    | 製品、会社、ロール、環境、実行条件                 |
| 設計内容      | 入出力、設定値、処理、ルール、状態変化             |
| 例外・復旧    | エラー検知、通知、再処理、取消、責任者             |
| 根拠・状態    | 参照仕様の版・節、判断理由、未確認／確認済／承認済 |
| 検証観点      | 入力例、期待値、確認する画面・出力・ERP 結果       |

未決事項は「課題 ID、関連要件／設計 ID、質問、影響、確認先、期限、回答・根拠、決定者、状態」で管理する。

## 7. 後続の試験自動化に向けて設計時に残す情報

README の「Playwrite」はブラウザ自動化ツールの Playwright を指す想定。ただし今は実装せず、設計から試験へ引き継ぐ情報を残す。

- 要件 ID → 設計 ID → 試験観点の対応。
- 利用ロール、前提状態、テストデータ、操作、期待結果、後片付け・再実行条件。
- 正常系に加え、権限違反、境界値、未突合、重複、連携失敗、取消、締め済期間のケース。
- UI で確認する結果と、連携ログ・出力ファイル・ERP 側で確認する結果の区分。
- 検証環境、SSO／MFA、データ準備、非同期処理の完了条件など、自動化の成立条件と制約。

ブラウザ操作の成功だけでは、ERP への反映や会計結果の正しさを検証したことにはならない。処理ごとに最終的な期待結果と証拠の取得先を決める。

## 8. 設計完了の判断基準

- 対象要件すべてに設計の対応先、または承認された対象外理由がある。
- 実際に利用する製品・設定・連携方法の実現性を確認している。
- 業務ルール、項目マッピング、権限、承認、例外・再処理が具体的に記載されている。
- BL と ERP の責任分界、正本、反映完了の判断、金額・件数の整合性確認が明確である。
- 未決事項に責任者と扱いがあり、確定を妨げる事項が解消されている。
- 業務、BL、ERP、運用それぞれの担当者が関連部分をレビューしている。
- 後続担当が設計から設定作業と期待結果のある試験項目を起こせる。

## 9. 構想検討での使い方

一つの仮想業務を選び、この一覧から必要情報を抽出する。各情報について「何の判断に使うか」「誰・どの資料から得るか」「どう取得するか」「得られない場合にどう扱うか」を書き出し、二つの Agent の受け渡し案を検討する。実案件の要件定義書をこのリポジトリに配置することは前提にしない。
