# プロセス・情報収集・Agent 分担の構想

## 1. 検討の目的

別プロジェクトで情報収集 Agent と設計 Agent を作るための判断材料をそろえる。以下は検討用の初期仮説であり、採用済みの仕様ではない。

| テーマ       | 答えたい問い                               | 成果物                         |
| ------------ | ------------------------------------------ | ------------------------------ |
| プロセス     | 要件から設計まで何をどの順で判断するか     | 工程、依存関係、開始・完了条件 |
| 必要情報     | 各判断に何が必要で、どの粒度なら使えるか   | 情報分類、必須項目、具体例     |
| 情報の用意   | どこから、どう取り出し、不足をどう埋めるか | 収集案、質問・検証方法         |
| Agent の分担 | 収集側、設計側、人が何を担うか             | 責任分界、受け渡し、差戻し条件 |
| 品質         | 情報と設計が十分か、どう判断するか         | 評価シナリオ、評価基準、失敗例 |

## 2. 将来の業務プロセス案

設計判断から必要情報を特定し、収集と設計を往復する方式を候補とする。

| 工程               | 行うこと                                   | 出力・次へ進める条件                     |
| ------------------ | ------------------------------------------ | ---------------------------------------- |
| 要件の整理         | 業務、対象、制約、期待結果、曖昧さを抽出   | 要件一覧と質問候補。原文との対応が分かる |
| 設計判断の分解     | 決めることと、それに必要な根拠を整理       | 判断項目と情報要求。収集目的が明確       |
| 情報収集           | 資料の探索・抽出、質問案、環境確認案を用意 | 出典・適用範囲付きの情報と不足一覧       |
| 情報の評価         | 版、対象環境、矛盾、裏付けを確認           | 採用できる根拠と保留事項を区別できる     |
| 設計案の作成       | 選択肢、制約、推奨理由、例外処理を整理     | 根拠のある設計案。未確定箇所が明示される |
| レビュー・追加調査 | 人の判断を求め、技術的な不足を収集側へ返す | 決定記録または具体的な追加情報要求       |
| 整合性確認         | 要件充足、領域間の整合、例外と復旧を確認   | 後続の設定・試験に引き継げる設計         |

このリポジトリでは、仮想例で各工程の入出力を書き出し、プロセスの妥当性を検討する。

## 3. 必要情報と用意する方法の案

資料の種類だけでなく「どの設計判断に使うか」と情報を結び付ける。

| 情報の層         | 例                               | 用意するためのアイデア                                     |
| ---------------- | -------------------------------- | ---------------------------------------------------------- |
| 案件の事実       | 対象会社、契約製品、ERP、取引量  | 案件プロフィールの質問票、契約・構成資料の確認             |
| 業務の意図と判断 | 消込の優先順位、許容差、承認責任 | 具体例付きの質問、現行手順の確認、選択肢の比較             |
| 製品の能力と制約 | 設定項目、連携仕様、利用条件     | 対象製品・版の公式資料、利用権限内の技術資料、ベンダー照会 |
| 環境の事実       | 有効な機能、既存設定、権限       | 設定エクスポート、管理者確認、許可された検証環境での観察   |
| データの実態     | キー、欠損、重複、通貨、例外     | 匿名化サンプル、項目定義、分布の調査、境界例の作成         |
| 設計の知識       | 判断手順、設計観点、失敗例       | 専門家レビュー、既存設計の一般化、適用条件付き事例集       |
| 決定の履歴       | 選択肢、理由、承認者、変更影響   | 判断記録、議事録との対応、変更時の再評価                   |

業務別の候補は [設計に必要な情報の候補](design-input-guide.md) を参照する。

## 4. 情報収集を成立させるアイデア

- 判断から逆算した質問票を作る。「未定だと何を決められないか」を付け、要件に回答があれば再質問しない。
- 情報分類ごとに資料の場所、管理者、閲覧条件、更新頻度を整理する。公開資料で不明な点は確認先を切り替える。
- 一般的な設計観点、製品仕様、案件固有の事実を分ける。過去案件の設定は適用条件を確認する。
- 金額や取引の例を提示し、期待結果と判断者を聞く。抽象的な質問だけで済ませない。
- 資料間の矛盾は、該当箇所と設計への影響を示した確認事項にする。
- 資料にない挙動は、仮説・確認手順・期待結果・取得する証拠をまとめて検証を提案する。実行権限や環境の利用可否は別途確認する。
- 要件や仕様の更新から、再調査すべき情報と再検討すべき設計を追える関係を残す。

今後、各案の自動化可能性、人の協力が必要な部分、取得コストを比較する。

## 5. Agent と人の責任分界案

| 担当               | 主な責任                                     | 渡すもの                                     |
| ------------------ | -------------------------------------------- | -------------------------------------------- |
| 情報収集 Agent     | 探索・抽出・出典整理・不足検知               | 根拠付き情報、矛盾、未取得理由、質問・検証案 |
| 設計 Agent         | 判断の分解、選択肢と設計案の作成、整合性確認 | 設計案、理由、影響、追加情報要求、判断依頼   |
| 業務責任者・専門家 | 業務方針の決定、適用確認、レビュー・承認     | 決定と理由、確認済みの事実、承認状態         |

要件整理と情報評価の担当は未決。初期案では、設計側が判断に必要な情報を定義し、収集側が根拠を整理し、設計側がその判断に使えるか評価する。

## 6. 受け渡す情報の最小構成案

実装形式より先に、意味として必要な項目を検討する。

| 受け渡し                  | 含めたい内容                                                                  |
| ------------------------- | ----------------------------------------------------------------------------- |
| 設計側 → 収集側：情報要求 | 要求 ID、関連要件、決めたいこと、必要情報、対象製品・環境、必要な粒度、優先度 |
| 収集側 → 設計側：収集結果 | 要求 ID、事実、出典と該当箇所、版・確認日、適用範囲、確認状態、矛盾、不足     |
| 設計側 → 人：判断依頼     | 論点、選択肢、根拠、影響、推奨案、判断が必要な理由                            |
| 設計側 → 収集側：追加要求 | 既存情報で判断できない理由、追加確認の条件、関連設計案                        |

事実、推論、提案、人の決定を区別する。出典だけで確定扱いにせず、今回の製品・環境への適用を確認する。未解決事項がある場合は、作業できる範囲と確定できない範囲を示す。

## 7. 机上で試す例

仮想要件：「入金と請求を照合し、消込結果を ERP に反映する」。検討用の例であり、製品機能の確定仕様ではない。

1. 設計側は、部分入金、複数請求への配賦、過不足、取消、ERP 反映失敗の判断項目を挙げる。
2. 収集側は、業務方針、製品仕様、ERP 受入仕様、データ例を必要情報として整理する。
3. 部分入金の方針は業務担当、設定可否は製品資料、再送時の重複防止は連携担当、と情報要求を振り分ける。
4. 設計側は根拠から案を作り、業務上の許容値を製品仕様から推測していないか確認する。
5. ERP 反映後に応答だけが失われる例を追加し、二重反映を避けるための情報要求と設計判断が出てくるか確認する。

この記録から質問票、情報記録、受け渡し項目、評価観点を改善する。

## 8. 評価方法と今後の検討順序

通常処理に加え、情報不足、資料の矛盾、環境差、実現できない要件、連携途中の失敗を含むシナリオで確認する。

- 設計判断ごとに必要情報と入手先を説明できるか。
- 不足を具体的な質問・調査・検証へ変換できるか。
- 未確認情報を確定扱いにせず、要件と根拠までたどれるか。
- 追加調査で不足が減り、同じ質問を繰り返さないか。
- 人が決める方針と Agent が支援する作業を区別できるか。

次は代表シナリオで「要件 → 判断項目 → 必要情報 → 収集案」の対応表を作り、一つの判断を深掘りする。その後、別シナリオで共通部分と業務固有部分を見極める。

別プロジェクトへは、プロセス定義、情報カタログ、収集方法・質問例、受け渡し仕様、判断・レビュー方針、評価シナリオ、未決事項一覧を引き継ぐ。実装技術の選定はこれらの要求が見えてから行う。
